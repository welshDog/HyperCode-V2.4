## ✅ Healer host-load guard built + rolled out (2026-10-13 ~18:22 BST)

- **Why:** the restarts that made things worse today all happened while the VM was starved (core costs ~90 s of downtime per restart; the dashboard's restart under build load, 12 Oct 13:30Z at CPU pressure ~73-85 %, left it with a missing rootfs and an unhealthy probe for ~19 h). Probe failures during a spike are usually the load, not the service.
- **What it does (PR #592, `2339fca3`, `agents/healer/mape_k_engine.py`):** while the guard is active the healer **holds docker/http restarts** (alert_only is never held). Signals, all VM-wide and readable by the healer's non-root user (`/proc/loadavg`, `/proc/pressure/cpu`, `/proc/meminfo` are not namespaced): CPU pressure (PSI "some" avg10) >= **50 %**; 1-min load per CPU >= **2.0** (4 CPUs here -> load >= 8); optional low MemAvailable (`HEALER_LOAD_GUARD_MIN_MEM_MB`, **off** by default because this stack normally sits at 1.4-1.6 GB); and **systemic** = >= 2 services that were healthy in the last 300 s went unhealthy together (services down for days, like the stopped observability stack, are not counted). **Fails open** if `/proc` is unreadable; a held service is **restarted anyway after 10 min** (`HEALER_LOAD_GUARD_MAX_HOLD_SECONDS`) so a real outage under sustained load still gets fixed; `HEALER_LOAD_GUARD_ENABLED=false` disables it. Look for `[GUARD]` log lines (WARNING when a hold starts or expires, INFO on release, once per hold, not every cycle). Every `HEALER_*` knob is documented in `agents/healer/README.md`.
- **Verified:** 41 tests in `agents/healer/tests/test_mape_k_policy.py` (21 existing + 20 new, incl. an end-to-end loop test: held under BUSY load, restarted once CALM; run in CI by `healer-policy-tests.yml`); the new engine run in a throwaway container from the healer image (Python 3.11, uid 1000) against the real VM kernel files: calm VM -> no hold, load 20 / PSI 83 % (like today's builds) -> HOLD, load 6 / PSI 30 % (merely busy) -> no hold; and, after the rollout, the same functions run inside the live `healer-agent`: `HostLoad(loadavg1=2.56, ncpu=4, cpu_pressure10=11.25, mem_available_mb~1580)`, decision no hold.
- **Rolled out:** image `a8f0dcd62a1b` (rollback tag `hypercode-v24-healer-agent:pre-load-guard-20261013` = `ad6d3677b3da`, the logging-fix version). Build took ~2.5 min on cached layers, lowest WSL available **1456 MB without stopping `fcc-proxy`**; the healer was recreated at 18:22 BST after waiting ~9 min for the post-build VM spike (load up to 13, PSI up to 81 %) to clear. Healthy, 0 restarts, `MAPE-K Engine ONLINE`; 35 running, 0 unhealthy; core (11:42Z) and dashboard (14:35Z) start times unchanged; no `[GUARD]` lines yet (calm VM, as expected).
- **First real-world activation observed (2026-10-13 17:58:21Z, during the alert-quieting rollout):** `[GUARD] host-load guard ACTIVE -- docker/http restarts are held: CPU pressure 63% >= 50%; load 10.5 on 4 CPUs` (the post-build VM spike), `cleared -- restarts allowed again` at 17:59:03Z (~42 s). No restart was pending, so it held nothing: this confirms the active/clear transitions and thresholds fire live, not that a held restart was released.
- **Still not tested against a real held restart.** The thresholds come from this VM (calm: load 1-5 / PSI < 30 %; builds: load 10-20 / PSI 40-85 %) and may need tuning after real events. A live test would be to stop `hypercode-ollama` WHILE the VM is loaded and look for `[GUARD] ... restart HELD`, then a restart after the load clears. It means inducing load on this 8 GB host (risky): ask Lyndz first, or wait for a natural spike.
- **Trade-off:** a genuinely failing service can now wait up to 10 min for its restart while the host is loaded; the 3-consecutive-probe rule and the post-restart verification are unchanged.

- A path-less "Python" Trivy target with `AnalyzedBy: sbom` = a vendored `bom.cdx.json`, not an installed package.
- `workflow_dispatch` only works for workflows already on `main`; to run a PR-branch workflow use `gh run rerun <run-id>`.
- Python heredocs collapse `\`-newline continuations (write scripts with the Write tool); read `docker-push.yml` as UTF-8.
- Wait for pending PR checks before merging (I merged #571 with three still pending; they passed).
- A PR that adds a check for a not-yet-published image to `images-integration.sh` makes that workflow fail on the PR (`manifest unknown`) until the image exists; merge, let the push run publish it, then re-run `gh workflow run images-integration.yml` (it passed 40/40 after #588).
