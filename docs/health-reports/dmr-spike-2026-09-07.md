## Decision gate

> **DMR answers the Ollama-native API → Phase 4 takes the CONFIG-SWAP route.**

The code migration (rewriting `backend/app/llm/ollama.py`, `brain.py`, ~6 agents,
3 test files to an OpenAI client) that was pre-approved as the ceiling **is not
needed**. Consumers keep calling `/api/tags` + `/api/generate` + `/api/chat`
unchanged; only the endpoint host and model names change.

## Config-swap scope (for Phase 4)

Small, all config — no application code:

1. **Endpoint** — every `OLLAMA_HOST` / `OLLAMA_BASE_URL` / `OLLAMA_URL` /
   `LLM_BASE_URL` currently `http://hypercode-ollama:11434` → repoint at
   `http://model-runner.docker.internal` (or keep the name via a `provider:
   {type: model}` service still called `hypercode-ollama`, or a compose
   `models:` block that injects the URL). Files: `docker-compose.core.yml:119`,
   `docker-compose.agents.yml` (agent-x ~700, coder-agent ~1030, pets ~1180,
   core dup ~810), `docker-compose.brain.yml:120`, `docker-compose.registry.yml:153`,
   `docker-compose.mcp-gateway.yml:235`, `.env:53`.
2. **Model names — NOT 1:1 (review gap, 2026-09-07).** Current Ollama names vs
   DMR `ai/` catalog:

   | Ollama name (now) | Used by | DMR path |
   |---|---|---|
   | `qwen2.5-coder:3b` | agent-x, `.env` | `ai/qwen2.5-coder` ✅ in catalog |
   | `qwen2.5:3b` / `:7b` | coder-agent, pets | `ai/qwen2.5` ✅ in catalog |
   | `phi3` / `phi3:mini` | preferred list, mcp-gateway backend-specialist | **no `phi3`** — catalog has `ai/phi4`; either move to phi4 or HF-GGUF pull |
   | `tinyllama` / `tinyllama:latest` | preferred list, brain default, boot.ps1 | **not in `ai/` at all** — HF-GGUF pull, or switch brain's tiny model to `ai/smollm2` (already cached, 256 MiB) |

   Gaps pull straight from Hugging Face as OCI artifacts, no catalog needed:
   ```
   docker model pull hf.co/<user>/TinyLlama-1.1B-Chat-v1.0-GGUF:Q4_K_M
   ```
   **Build the full old→new map, `docker model pull` every entry, and only then
   delete `hypercode-ollama`** — never leave an agent pointing at a name DMR
   doesn't have. All config, no code.
3. **Model-size filter** — DMR `/api/tags` returns `"size":0`;
   `select_best_ollama_model()` compares against `OLLAMA_MAX_MODEL_SIZE_MB`.
   Verify a 0 size doesn't wrongly include/exclude models; if it does, raise or
   disable `OLLAMA_MAX_MODEL_SIZE_MB` (env only).
4. **Model ref format** — resolver must tolerate `name` = `docker.io/ai/smollm2:latest`
   (registry prefix + slashes). Confirm `OllamaModelResolver` pattern matching
   handles it; if not, it's a small regex/config tweak, still not a rewrite.
5. **Remove** the `hypercode-ollama` service (`docker-compose.core.yml:183`), the
   GPU variant, and override stubs (`on-demand.yml`, `nano.yml`, `dev.yml`) —
   or repurpose the name as the provider shim.
6. **Warm-up** — `scripts/boot.ps1` STEP 12 `ollama pull tinyllama` →
   `docker model pull <chosen models>` (or drop; DMR pulls on first use).
7. **Docs** — rewrite `docs/DOCKER_MODEL_RUNNER.md` (currently Ollama relabelled),
   fix stale `docker exec model-runner ollama pull` in `scripts/mcp-gateway-start.sh`.

**Rollback path** stays `docker-compose.hosted-llm.yml` (agents → Anthropic).

## Phase 4 order (revised after review)

1. **Build the model map** (table above) incl. HF-GGUF fallbacks for
   `phi3`/`tinyllama`; `docker model pull` every entry; check total disk.
2. **Repoint** `OLLAMA_HOST` → `http://model-runner.docker.internal:12434` —
   or the `provider:`-shim service still named `hypercode-ollama` so nothing
   else needs touching (test `provider:` support in compose v5.5.1 first).
3. **Size-filter env tweak** for the `/api/tags` `"size":0` quirk.
4. **Smoke test from every network**, not just agents-net (see 3b) — from each
   consuming service.
5. **Only then** stop + remove `hypercode-ollama`; keep `docker-compose.hosted-llm.yml`
   as rollback for a full day.

## Expectation to set

**5 min TTL ⇒ cold start.** The first inference after an idle period reloads the
model from disk before the first token. Bursty agent traffic will occasionally
see a slow first response. Same RAM-lifecycle win as Phase 2's `KEEP_ALIVE=5m`,
just done natively — the latency characteristic is identical, not new.
